# Writing a project page

The page is written for a teammate who has never opened the repository. It
explains what the project is for and how it fits with the rest of the team's
work, not what every file contains. The README is an input, never the output.

## Procedure

### 1. Locate the docs and the source

Follow `ds-docs-locate`. The project is the repository you are in, or the path
or URL given. Record the remote URL and current commit; they go in the
`doc-metadata` comment.

```bash
git remote get-url origin
git rev-parse --short HEAD
```

### 2. Read the repository, in this order

1. `README.md`, `CLAUDE.md`, `AGENTS.md`, `docs/` for stated intent.
2. The manifest for the stack: `pixi.toml`, `pyproject.toml`, `package.json`,
   `docker-compose*.yml`, `Dockerfile`, `dock.yaml`.
3. Entry points and CI: console scripts, `Makefile`, `.gitlab-ci.yml`,
   `Jenkinsfile`, DAG or flow definitions.
4. `git log --since='6 months ago' --format='%cs %s' | head -40` for what is
   actually active.

Stop reading when you can answer: what does it produce, who consumes that,
where does it run, and how does a teammate run it. Do not inventory files.

### 3. Write the page

If the repository is registered in `sync.config.local.json`, run `npm run sync`
first. It creates the page from the template with the frontmatter and a facts
block filled in, or refreshes the facts block on an existing page. Never edit
between the `<!-- sync:facts:start -->` and `<!-- sync:facts:end -->` markers;
the next sync overwrites them.

Otherwise copy `templates/project-page.md` to `docs/wiki/projects/<name>.md`,
where `<name>` is the repository name in lowercase with hyphens.

Replace every italic prompt with real content and remove the
"Awaiting a writer" admonition. Rules that the lint enforces:

- Frontmatter: `title`, `description`, `tags`, `related`, `status`,
  `last_reviewed` (today). `owner` is a team or role, never a person.
- `related` lists other project pages by file name without `.md`, and each must
  exist. Add the reciprocal link on the other page.
- Hosts, accounts, and paths that identify the organization use placeholders:
  `gitlab.example.com`, `<account>`, `<compute-pool>`. Command examples show
  variable names, never values.
- Plain Markdown. No raw HTML, no MDX.

If the page already exists, keep hand-written sections that are still accurate
and update the rest. Bump `last_reviewed`. Note what changed in the commit
message.

### 4. Connect it

- The table in `docs/wiki/projects/index.md` is generated by the sync from
  registered projects. If the project is not registered, add it to
  `sync.config.local.json` and run `npm run sync`; do not hand-edit the table.
- If the repository has ADRs, add rows to `docs/wiki/adr-index.md` with
  `ds-wiki-adr`.
- Record the addition with `ds-wiki-change` so the changelog shows it.

### 5. Verify

```bash
npm run lint
```

Zero errors in the files you touched. Then commit.

## What not to do

- Do not paste the README. Summarize it.
- Do not describe unreleased or planned features as if they exist.
- Do not include credentials, tokens, IPs, internal hostnames, account
  locators, or people's names. The lint blocks the ones it can detect; you are
  responsible for the rest.
